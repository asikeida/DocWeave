# 骨架收尾验收

对应 Issue #9，分支 `infra/skeleton-骨架收尾验收`。本记录区分自动测试、真实数据库验证和仍需在业务阶段完成的验证。

## 本轮发现与修复

此前 POM 只有 flyway-core 和 flyway-mysql，Spring Boot 4 的 Flyway 自动配置模块没有进入运行时。新增回归测试在旧依赖下实际失败：Flyway Bean 不存在。改为 spring-boot-starter-flyway 后，历史表初始化及迁移测试通过。

MySQL Compose 端口改为仅绑定 127.0.0.1；健康检查改为应用账号登录目标数据库执行 SELECT 1。应用通过已有 Maven Wrapper 与环境变量启动，文档分别说明 Windows、Linux / macOS 和 IDE 的方式，不引入专用启动脚本依赖。

## 如何复现

先按 [本地开发环境](01-本地开发环境.md) 配置 .env、启动 Compose MySQL，再按所在系统设置环境变量，通过 Maven Wrapper 或 IDE 启动应用，检查健康接口和 Swagger。

```powershell
./mvnw.cmd --batch-mode --no-transfer-progress verify
```

启动日志应出现 Flyway 的数据库识别、验证和迁移结果。没有业务迁移时，Flyway 历史表为空是正常状态，不能以“执行 0 个迁移”推断 Flyway 没有接入。

## 业务与部署边界

- 目前没有生产业务表，不创建无用途的 V1。首个业务迁移由 M1 用户与工作空间模块提交，并与 JPA 实体一起验证。
- 测试夹具的 V1 只用于独立验证，不占用生产数据库的版本号，也不能直接复制到正常开发库。
- 本地验证不等同于生产部署；staging 配置、服务器 Docker 隔离、Nginx、HTTPS、备份及自动部署留到部署阶段实施。
- 真实用户权限、跨工作空间隔离、注册登录仍待 M1，不属于当前骨架的已实现能力。
- 暂未在全新操作系统重新安装全部工具；本轮验证使用现有 JDK、Docker Desktop 和依赖缓存。

参考：[Spring Boot 数据库初始化](https://docs.spring.io/spring-boot/how-to/data-initialization.html)。


日常开发随后切换到独立云端 MySQL，本机 Docker 改为可选。云端部署、SSH 隧道、持久化及应用连接的实际结果见 [云端开发数据库与 DBeaver](06-云端开发数据库与DBeaver.md)。
