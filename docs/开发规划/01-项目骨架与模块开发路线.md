# DocWeave 项目骨架与模块开发路线

> 文档状态：规划稿
> 适用阶段：项目初始化至首个可公开演示版本
> 当前原则：先搭建稳定骨架，再按业务闭环逐个开发模块
## 1. 项目目标

DocWeave 是一个兼顾个人使用、企业内部知识协作和求职展示的智能文档知识库。个人区域和企业区域以组织为边界隔离，成员在组织、空间和知识库的授权范围内上传和查询文档，系统完成解析、切分、索引和检索，并在问答时给出可追溯的引用来源。

企业权限方案当前为待审提案，详见 [企业场景与权限模型](../架构设计/01-企业场景与权限模型.md)、[RAG 授权与撤权设计](../架构设计/02-RAG授权与撤权设计.md) 和 [M1 计划](03-M1账号与工作空间实施计划.md)。未实现的企业能力不能作为当前功能展示。

首个公开版本需要同时满足三类目标：

1. **能使用**：完成注册登录、知识库管理、文档上传、检索问答和历史记录。
2. **能展示**：公开网站具有完整体验，关键功能可演示，架构和工程实践便于面试讲解。
3. **能演进**：基础设施和业务代码边界清晰，后续可以加入多租户、异步处理、模型切换和监控。

项目不以堆积中间件或拆分微服务为目标。每项技术都应由当前业务问题引入，并能够解释它解决了什么问题。

## 2. 总体技术基调

### 2.1 应用形态

- 前后端分离，放在同一个 Git 仓库中管理。
- 后端采用 Spring Boot 模块化单体。
- 前端采用 Vue 3、TypeScript 和 Vite。
- 前后端分别构建，生产环境由 Nginx 托管前端并反向代理后端接口。
- 日常开发通过 SSH 隧道连接云端开发 MySQL，本机 Compose 为可选方案；应用代码由 IDE 或 Maven Wrapper 运行。
- 生产环境逐步容器化，通过 GitHub Actions 构建和发布。

### 2.2 当前版本基线

- Java 21
- Spring Boot 4.1.1
- Maven Wrapper
- MySQL
- Spring Data JPA
- Bean Validation
- Spring Boot Actuator
- Lombok

现有初始化依赖只构成后端起点。Redis、MinIO、Kafka、Elasticsearch、OpenAPI、Flyway 和安全组件应在对应阶段按需加入。

### 2.3 单仓库目录约定

```text
DocWeave/
├─ src/                       # Spring Boot 后端源码
├─ frontend/                  # Vue 前端工程
├─ docs/                      # 架构、开发和部署文档
│  ├─ 开发规划/
│  ├─ 架构设计/
│  ├─ 接口说明/
│  └─ 部署运维/
├─ deploy/                    # Nginx、容器和部署配置
├─ scripts/                   # 可重复执行的辅助脚本
├─ .github/workflows/         # GitHub Actions
├─ compose.yaml               # 本地基础设施
├─ AGENTS.md                  # AI Agent 的仓库级工作约定
├─ README.md                  # 面向开发者和项目访客的入口
├─ pom.xml
├─ mvnw
└─ mvnw.cmd
```

Spring Boot 暂时保留在仓库根目录，不为了目录对称而迁移到 `backend/`。这样 Maven Wrapper、IDE 和现有初始化结构都可以直接使用。前端仍是独立工程，前后端分离不依赖目录名称。

## 3. 后端代码组织方式

后端采用“按业务功能分包”，避免把所有 Controller、Service、Repository 分别堆在全局目录中。

```text
me.asikeida.docweave
├─ common/                    # 通用错误、响应、工具和跨模块类型
├─ config/                    # Spring 与基础设施配置
├─ auth/                      # 认证、令牌和当前用户
├─ user/                      # 用户资料与账号状态
├─ organization/              # 企业、企业成员与部门（随 M1 实现时加入）
├─ workspace/                 # 工作空间、成员和权限边界
├─ knowledgebase/             # 知识库
├─ document/                  # 文件元数据、上传和处理状态
├─ ingestion/                 # 解析、切分、向量化和索引流程
├─ retrieval/                 # 搜索、召回和重排
├─ chat/                      # 对话、消息、引用和历史记录
└─ admin/                     # 管理与运行状态
```

每个业务包内部按需要使用以下层次：

```text
feature/
├─ controller/                # HTTP 边界、参数校验
├─ service/                   # 用例编排和事务边界
├─ domain/                    # 实体、值对象、业务规则
├─ repository/                # 持久化接口与实现
└─ dto/                       # 请求、响应及内部传输对象
```

小模块无需机械地创建全部目录。只有出现真实职责时才新增对应类型。

## 4. 第一阶段：建立项目骨架

第一阶段不开发复杂业务，目标是建立后续所有模块共同依赖的工程基础。

### 4.1 仓库与协作约定

需要完成：

- 编写 `README.md`，说明项目定位、技术栈、运行方式和路线图。
- 编写根目录 `AGENTS.md`，记录仓库结构、编码约定、验证命令和敏感信息规则。
- 建立 `docs/` 目录和文档编号规则。
- 确认 `.gitignore` 覆盖 IDE、构建产物、日志、上传文件和本地环境变量。
- 提供 `.env.example`，只保留变量名称和安全示例，不提交真实密钥。
- 采用短生命周期功能分支和 Pull Request 工作流。

### 4.2 后端基础配置

需要完成：

- 建立 `local`、`test`、`prod` 配置边界。
- 通过环境变量读取数据库、令牌、对象存储和模型服务配置。
- 配置 MySQL 数据源与连接池。
- 引入 Flyway，所有数据库结构通过版本化脚本演进。
- 配置统一时区、JSON 日期格式和 UTF-8。
- 建立统一异常模型和明确的 HTTP 状态码。
- 建立请求参数校验错误的统一输出。
- 保留 Actuator 健康检查，只公开必要端点。
- 引入 OpenAPI 页面，接口定义随代码同步生成。

不急于建立过度统一的返回包装。如果 HTTP 状态码和响应结构已经清楚，就避免为了形式把所有内容塞进 `code/data/message`。

### 4.3 本地运行环境

第一版 `compose.yaml` 只启动 MySQL，后续再逐项加入其他基础设施。

需要完成：

- MySQL 容器与持久化卷。
- 数据库健康检查。
- 环境变量示例。
- 一条明确的本地启动路径：启动 MySQL，再由 IDE 或 Maven 启动后端。
- 为测试环境提供独立数据库策略，避免测试污染本地开发数据。

### 4.4 最小纵向验证

骨架阶段实现一个不含业务逻辑的验证闭环：

1. 应用可以连接本地 MySQL。
2. Flyway 实际参与启动并创建历史表；隔离测试验证迁移执行，首个业务 V1 随持久化模块交付。
3. `/actuator/health` 返回健康状态。
4. OpenAPI 页面可以打开。
5. 自动化测试可以在干净环境运行。
6. GitHub Actions 可以完成编译和测试。

### 4.5 骨架阶段完成标准

- 新人按照 README 可以在本机启动项目。
- 配置文件中没有真实密码、令牌和服务器信息。
- 数据库不是依靠 JPA 自动建表来维护。
- 本地、测试和生产配置的用途清楚。
- 后端编译、测试和健康检查均可重复验证。
- 尚未开发业务时，仓库已经具备清晰的提交和审查路径。

## 5. 业务模块开发顺序

模块按照“先形成可用闭环，再增加智能能力”的顺序推进。

### 里程碑 M1：个人与企业账号、组织及工作空间

目标：个人有独立区域，企业成员在明确授权的空间中协作，并具有可验证的组织数据隔离边界。个人与企业共用底层模型，界面按模式简化。

主要内容：

- 账号建立策略、登录、退出和当前用户接口；正式开放注册时事务内建立个人组织、本人 OWNER、默认空间及明确管理授权，不自动加入企业。
- 密码安全存储；会话或令牌方案在实现前记录决策，并验证撤销和退出。
- 企业、企业成员、邀请与停用；企业管理角色不等于内容阅读角色。
- 企业成员最多一个所属部门，支持待分配与调岗；明确选择 SELF/SUBTREE 授权范围，跨部门协作使用空间成员。
- 工作空间创建与用户、部门、全员授权；角色和内容范围分别判定。
- 后端鉴权与前端路由守卫。

验证场景：跨企业访问被拒绝；上级不能凭职位读取未授权项目；同企业成员只能访问有效授权空间，离职后旧登录凭据不能继续访问。

这一阶段再引入 Spring Security。Redis 是否加入取决于令牌撤销、验证码或限流等真实需求，不能只为了丰富技术栈而加入。

### 里程碑 M2：知识库与文档管理

目标：用户能够建立知识库并管理文档。

主要内容：

- 知识库的创建、编辑、归档和列表，以及 INHERIT/RESTRICTED 模式与人员排除；排除优先于允许授权。
- 文档元数据、上传、下载和删除。
- 同库重复上传检测、并发幂等、版本选择与逻辑删除；不同业务文档独立存储，不按全局内容哈希批量删除。
- 文件类型、大小和权限校验；文档完整继承知识库权限，对象存储私有。
- 文档处理状态与失败原因。
- 引入 MinIO 存储原始文件，MySQL 保存元数据。

验证场景：上传文件后，可以在知识库中看到准确状态；删除知识库时，数据库记录与对象文件的处理规则明确。

### 里程碑 M3：文档解析与异步处理

目标：把上传文件可靠地转换为可检索内容。

主要内容：

- PDF、Markdown、TXT 等首批格式解析。
- 文档切分策略与切片元数据。
- 处理任务的状态机：待处理、处理中、成功、失败。
- 重试、幂等和失败诊断；任务携带企业、文档版本与处理代次，旧任务不能复活已删除资源。
- 当同步处理已经成为请求耗时或可靠性问题时引入 Kafka。

验证场景：重复消费不会产生重复切片；处理失败后可以定位原因并安全重试。

### 里程碑 M4：索引与检索

目标：用户能够在自己的知识库中找到相关原文。

主要内容：

- Elasticsearch 索引设计。
- 关键词检索。
- 向量字段和嵌入模型适配层。
- 混合检索和结果排序。
- 企业、空间与允许知识库集合的检索预过滤，以及候选的权威状态和权限校验。
- 索引重建和删除一致性。

验证场景：相同问题能返回稳定、相关且属于当前用户的数据；删除文档后不能继续被检索到。

先把检索结果做对，再接入大模型生成答案。

### 里程碑 M5：基于证据的问答

目标：根据检索内容生成回答，并能够查看证据来源。

主要内容：

- 大模型供应商抽象，业务层不绑定单一厂商 SDK。
- 提示词模板和上下文长度控制。
- 首版缓冲完整答案，模型调用前和返回前复核授权；流式输出后续单独设计撤权和取消规则。
- 回答与引用片段的映射。
- 无充分证据时的回答策略。
- 模型调用超时、失败和费用信息记录；企业批准外发服务，保存实际上下文的完整来源依赖。

验证场景：每个引用能够回到具体文档和片段；历史记录再次打开后，引用仍然有效。

### 里程碑 M6：对话历史与用户体验

目标：形成可持续使用的完整产品体验。

主要内容：

- 会话和消息持久化到 MySQL，绑定企业、空间与会话所有者。
- 会话标题、列表、删除和继续对话。
- 引用预览、文档定位和反馈；历史回答、标题、摘要和继续对话均复核当前来源权限。
- 前端加载态、空状态、错误态和移动端适配。
- Redis 只用于短期上下文、缓存或会话辅助，不承担历史消息的永久保存。

验证场景：服务重启后有权用户仍能查看历史；来源失权后相关问答整轮隐藏，旧上下文不能再次送入模型。

### 里程碑 M7：公开演示与作品集呈现

目标：部署为可访问、可说明、可维护的求职作品。

主要内容：

- `docweave.asikeida.me` 作为项目访问地址。
- Nginx 提供 HTTPS、前端静态资源和 `/api` 反向代理。
- 独立个人试用与企业演示入口；企业演示提供只读非敏感资料，各体验账号聊天隔离，上传在个人区域进行。
- 示例知识库与非敏感演示数据。
- 项目架构图、功能截图、技术决策和问题复盘。
- 基础日志、健康检查、备份和资源监控。

采用同域名下的 `/api` 可以简化浏览器跨域和 Cookie 配置。域名、证书和服务器信息通过部署环境管理，不写入公开仓库的真实凭据。

## 6. 前端推进方式

前端不需要等待所有后端模块完成后再开始。每个业务里程碑都按照一个纵向功能切片推进：

1. 明确页面和用户动作。
2. 先定义接口请求、响应和错误语义。
3. 后端完成最小接口和自动化验证。
4. 前端完成页面、交互和异常处理。
5. 在真实浏览器检查网络请求和最终行为。
6. 一个闭环完成后再进入下一项。

首批前端基础包括：

- Vue 3、TypeScript、Vite。
- 路由、状态管理、HTTP 客户端和统一错误处理。
- 基础布局、设计变量和可复用表单组件。
- 登录页、应用框架页和 404 页面。
- ESLint、类型检查和生产构建命令。

组件库需要在确定视觉方向后选择，不在骨架阶段同时引入多套 UI 方案。

## 7. Git 分支、提交与发布原则

### 7.1 分支

- `main` 始终保持可构建、可部署。
- 每项工作从最新 `main` 创建短分支。
- 分支示例：`feat/auth-login`、`feat/document-upload`、`infra/local-mysql`、`docs/project-roadmap`、`fix/citation-preview`。
- 一个分支解决一个清晰问题，完成后通过 Pull Request 合并。
- 个人项目暂不维护长期 `develop` 分支。

### 7.2 提交

使用能表达意图的 Conventional Commits：

```text
docs: add project skeleton roadmap
infra: add local mysql compose service
feat(auth): add password login
feat(document): store uploaded file metadata
fix(chat): preserve references in history
test(retrieval): cover workspace filter
```

每个提交应满足：

- 只包含同一目的的改动。
- 能独立说明“为什么改”和“改了什么”。
- 不混入 IDE 文件、临时日志、构建产物和本地密钥。
- 在提交前运行与改动相关的最小验证。

### 7.3 发布

- 功能分支推送用于备份、协作和 Pull Request。
- Pull Request 通过 CI 后合并到 `main`。
- `main` 合并结果部署到在线演示环境。
- 阶段性可演示版本使用标签，如 `v0.1.0`、`v0.2.0`。
- 数据库迁移与应用版本一起发布，不在服务器上手工改表。

## 8. 测试与质量策略

测试围绕风险编写，不追求没有意义的覆盖率数字。

- 领域和服务测试：权限、状态流转、幂等和引用映射等业务规则。
- Repository 集成测试：JPA 查询、租户过滤和数据库约束。
- Controller 测试：认证、参数校验、状态码和响应结构。
- 基础设施集成测试：对象存储、Kafka、Elasticsearch 只覆盖关键适配逻辑。
- 前端测试：关键状态转换和高风险交互。
- 浏览器端到端测试：登录、上传、处理、问答和历史引用组成的主链路。

每个里程碑至少保留一条可以重复运行的主流程验收路径。

## 9. Docker 与环境隔离

### 本地开发

- 日常使用云端开发 MySQL 和 SSH 隧道，本机 Compose 可选；其他依赖随业务需要逐项加入。
- Spring Boot 和 Vue 默认由 IDE/本机进程运行，保留快速调试体验。
- 当需要验证完整部署时，再使用应用容器。

### CI

- 使用临时服务或 Testcontainers 运行集成测试。
- 构建后端 Jar、前端静态文件和 Docker 镜像。
- 镜像使用明确版本标签，不依赖 `latest` 判断发布内容。

### 生产

- 配置与镜像分离。
- 密钥只存在于部署环境。
- 数据目录使用持久化卷并建立备份策略。
- 所有服务设置健康检查和资源限制。
- 先满足单机或少量节点可靠运行，再评估高可用架构。

## 11. 推荐的下一步执行清单

接下来的实际工作限定在“骨架阶段”，建议按以下顺序完成：

1. 创建根目录 `AGENTS.md` 和 `README.md`。
2. 整理配置分层、`.env.example` 和敏感信息规则。
3. 创建只包含 MySQL 的 `compose.yaml`。
4. 接入并验证 Flyway；首个业务数据库迁移与持久化模块共同交付。
5. 配置本地、测试和生产 Profile。
6. 完成统一异常、参数校验和最小健康接口。
