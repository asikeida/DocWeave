# M1 个人与企业账号、组织及工作空间实施计划

> 状态：Issue #11 的待审核计划，尚未实现业务功能。
> 本稿按个人与企业双模式重写：注册建立独立个人组织，企业成员通过邀请加入。骨架 PR #10 已合并；当前只交付待审设计，不执行建表或业务开发。

## 1. 设计入口与阶段目标

先阅读 [企业场景与权限模型](../架构设计/01-企业场景与权限模型.md) 和 [RAG 授权与撤权设计](../架构设计/02-RAG授权与撤权设计.md)。角色、继承及撤权语义以这两份待审设计为准；审核确认后才能成为实现基线。

M1 的目标是账号可登录并拥有独立个人区域，成员可受邀加入企业，企业部门与协作空间可管理。个人和企业共用 tenant_id 隔离，任何请求都不能越过当前组织边界。知识库、文件与 RAG 分后续阶段交付，个人区域在 M1 不伪装成完整知识管理功能。

M1.2 只建立个人默认空间及直接角色所需的最小数据结构与操作，不提前交付完整企业空间授权界面；M1.4 再扩展企业空间的创建、部门/全员授权和角色管理。迁移按依赖顺序追加，避免注册依赖一张尚未创建的空间表。

## 3. M1.1 动代码前的认证决策

前后端采用同域 /api 的浏览器应用形态。优先评估 Spring Security 服务端会话与 HttpOnly Cookie；这仍是候选方案，不能直接默认为最终选型。若采用访问令牌，必须明确浏览器保存、过期、撤销、刷新与退出失效机制，不只是在前端删除令牌。

实施前形成一份简短决策记录，明确：

1. 会话或令牌的存储、失效策略、账号停用后的实时核验；重启与多实例行为。
2. Cookie 的 Secure、HttpOnly、SameSite、路径，开发环境与 HTTPS 的差异；CSRF/CORS 策略。
3. 公开账号注册是否开启、邀请如何衔接注册与已有账号，以及登录失败提示与限流边界。
4. 首账号与首企业的受控创建方式，禁止无保护的初始化管理接口；不把账号密码或邀请令牌写进迁移脚本。
5. 会话只确认身份，不长期固化企业/空间全部权限；每次业务请求重新核对当前企业成员与授权。

M1.1 先交付账号身份；正式开放注册须等 M1.2 同时具备个人组织初始化，避免用户注册后无可用区域。注册时在同一事务建立账号、个人组织、唯一 OWNER 成员、默认空间及直接 ADMIN 授权；若为已有账号补建则幂等执行。不自动加入企业。个人组织最多一个成员，不能邀请同事或建立部门。

M1.1 可用隔离测试数据验证账号和登录，不依赖已存在的企业管理功能。正常业务未实现前保持关闭，不能为绕过 Security 全局 permitAll。

## 4. 迁移、模块与数据库约束

- 首个持久化交付创建用户表的 V1，具体脚本名随实现确定；企业、邀请、部门和空间按后续交付追加迁移，不把整个未来模型预建进 V1。
- 新增 organization 模块承载企业、企业成员与部门；auth 管认证，user 管账号，workspace 管协作空间。只在实现职责出现时创建包，不提前建空目录。
- 个人组织与默认空间在 M1.2 随真实用例交付；个人页面隐藏企业部门和成员配置，后端同样禁止这些操作。公开注册前落实反滥用与配额，企业演示使用独立体验账号与只读预置资料。
- 跨模块授权逻辑通过明确服务接口复用；列表查询的范围生成与单资源判定必须来自相同规则，不能每个 Controller 各写一套。
- 企业资源显式携带 tenant_id，并以同企业关联约束及 Service 校验防止跨企业引用；用户账号本身是全局身份。
- 企业成员的 OWNER/ADMIN/MEMBER 与空间 ADMIN/EDITOR/READER 分开；不在 users 上放一个全局 ADMIN 来代表全部企业权限。
- 首版通过授权关系表达成员资格，不用逗号字符串保存部门和权限。创建者字段仅用于审计。
- 企业、成员状态与授权版本是后续 RAG 的权威依据；改变权限的事务同时写入审计和递增版本，回滚时全部回滚。
- 首批开发库操作前需要备份与隔离 MySQL 验证；不在共享开发库反复清空数据，不修改已执行的迁移历史。

## 5. 测试与接口交付

后端运行 Maven Wrapper verify；H2 快速测试之外，涉及业务约束的迁移必须在隔离真实 MySQL 验证，建立可重复的集成测试路径，不能只靠人工点一次。

- M1.1：成功/失败登录、密码不泄漏、退出、失效、过滤器 401/403 与 ApiError/requestId 一致。
- M1.2：个人组织幂等初始化与回滚、个人成员上限、禁止跨个人组织访问；并发邀请、失效与防提权、成员停用、OWNER 保护、组织切换。
- M1.3：跨企业父部门与成员引用、循环层级、子部门展开及调岗。
- M1.4：不同角色的读写、授权来源合并、越权授权、猜 ID、最后管理员交接与成员停用后的封闭行为。
- M1.5：两个企业、多个部门和跨部门项目的浏览器验收；管理者不因企业角色取得未授予的空间内容权限。

前端运行 lint、typecheck、test、build，检查表单、加载/错误状态、真实请求和身份切换后的旧数据清理。OpenAPI 与认证调试说明随各个接口交付，不等到阶段结束补齐。

## 7. Git 与审核流程

本设计阶段对应 Issue #11，分支 docs/enterprise-企业权限与RAG设计。当前阶段只写文档，审核前不 commit 或 push。

后续实现分别创建 Issue，例如分支 feat/auth-login-账号登录、feat/organization-企业与成员、feat/department-部门结构、feat/workspace-空间授权。提交使用中文 Conventional Commits，例如 feat(workspace): 新增部门与成员的空间授权。

同一闭环所需迁移、业务、测试与文档一起审查。PR 使用 Closes #实际编号，通过 CI 后由用户审核合并；不把后续业务混入本次设计 PR。

当前云端开发库与 SSH 隧道保持不变；本轮不部署新服务，不引入 Nacos、Kafka、Elasticsearch、MinIO 或权限引擎。Redis 是否需要由认证决策决定。
