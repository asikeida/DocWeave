# 注释与命名规范

## 1. 命名是第一层文档

优先通过准确的英文命名表达含义，避免让注释替代码翻译名称。

- 包名全小写，使用英文单词，不使用拼音、下划线或无意义缩写。
- 类、接口、枚举使用 UpperCamelCase，名称表达领域概念或职责，例如 `DocumentProcessingJob`。
- 方法、参数、局部变量使用 lowerCamelCase，名称表达动作或状态，例如 `createKnowledgeBase`、`workspaceId`。
- 常量使用 UPPER_SNAKE_CASE，名称表达不可变业务含义，例如 `MAX_UPLOAD_SIZE_BYTES`。
- 布尔值使用能读成判断句的名称，例如 `isArchived`、`hasAccess`、`canRetry`。
- 缩写只使用广泛约定的技术术语，例如 `URL`、`HTTP`、`ID`、`DTO`。不要自创缩写。
- 名称不应携带无用实现细节，例如避免 `userListServiceImpl2`、`dataProcessUtil`。

## 2. 何时写 Javadoc

`/** ... */` 是 Java 的 Javadoc，用于说明调用者需要知道的契约。它不应被禁止。

以下场景必须或应当使用 Javadoc：

- 对其他模块暴露的公共接口、扩展点和非直观的 public 方法。
- 配置属性类，说明配置项的用途、单位、默认行为和安全影响。
- 业务术语不明显的领域类型、值对象和枚举。
- 有重要前置条件、返回约束、异常语义或副作用的方法。

Javadoc 应说明如何使用、输入输出约束、失败语义和必要的限制。简单 getter、显而易见的构造器、只在本类使用的私有辅助方法不要求为了形式补 Javadoc。

示例：

```java
/**
 * 根据当前工作空间创建知识库。
 *
 * @throws AccessDeniedException 当前用户不是该工作空间成员时抛出
 */
KnowledgeBase create(CreateKnowledgeBaseCommand command);
```

## 3. 行内和块注释

- 单行 `//` 注释用于解释代码本身无法表达的“为什么”：业务取舍、兼容性原因、边界条件或外部系统限制。
- 复杂算法、状态机或不直观分支可以使用 `/* ... */` 块注释说明整体思路。
- 注释优先使用中文；协议名、类名、配置名、代码标识符保留英文。
- 不注释显而易见的代码，例如“获取用户”“循环列表”“返回结果”。
- 注释修改后必须与代码一致；过期注释比没有注释更危险。

好的注释：

```java
// 索引删除通过异步任务执行，避免同步请求与对象存储删除竞争。
enqueueIndexDeletion(documentId);
```

无价值注释：

```java
// 创建知识库
knowledgeBaseRepository.save(knowledgeBase);
```

## 4. TODO 和临时方案

不允许无归属、无期限的 `TODO`、`FIXME` 或“临时实现”留在正式代码中。

确实需要暂缓的工作，必须先建立 GitHub Issue，并写成可追踪格式：

```java
// TODO(#42): 接入病毒扫描服务后再允许 office 文件上传。
```

Issue 关闭前应删除对应 TODO。不能用返回 `null`、空集合、固定成功结果或模拟生产数据来伪装未完成实现；测试夹具和明确标识的开发样例除外。

## 5. Java 注解与 Lombok

- 重写父类或实现接口的方法，在语言允许时使用 `@Override`。
- API 请求对象用 Bean Validation 注解表达输入约束。
- JPA Entity 不使用 Lombok `@Data`，避免自动生成的 `equals`、`hashCode`、`toString` 与代理、关联关系或敏感字段发生问题。
- DTO 可优先使用 Java `record` 表达不可变数据；需要 Lombok 时按实际需求选择 `@Getter`、`@Builder` 等，不要求机械叠加全部注解。
- `toString` 不输出密码、令牌、完整文档内容或大字段。

## 6. 格式化

格式由后续引入的自动格式化工具统一处理。当前阶段遵循现有代码风格：四空格缩进、一个顶级 public 类对应一个文件、导入有序、避免为了对齐而改动无关行。

不要将大范围格式化与功能改动放在同一提交或 Pull Request。
