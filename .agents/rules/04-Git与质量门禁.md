# Git 与质量门禁

## 1. 总体工作流

DocWeave 从第一个正式工程任务开始，使用下面的闭环：

```text
Issue → 从最新 main 创建短期分支 → 小步提交 → 本地验证 → Pull Request → 审核 → 合并 main → 删除分支
```

`main` 始终保持可构建、可部署。不要直接在 `main` 开发正式功能。

仓库初始化是唯一例外：首次由 Spring Initializr 生成的最小工程可以直接提交到 `main`，提交后立即进入正常分支流程。

一个里程碑可以包含多个 Issue；一个 Issue 可以包含多个清晰 commit；一个 Pull Request 原则上只解决一个 Issue 或一组不可拆分的紧密问题。不要把“一个阶段”机械地压成一个巨大提交。

## 2. 分支命名

分支格式：

```text
<类型>/<简短主题>
```

规则：

- 类型与主题使用小写英文和连字符。
- 主题说明目标，不使用姓名、日期或无意义编号。
- 分支应短期存在，PR 合并后删除。
- 从最新 `main` 创建；如果 `main` 有新提交，优先在合并前同步并解决冲突。

推荐类型：

| 类型 | 使用场景 | 示例 |
| --- | --- | --- |
| `feat` | 新用户能力 | `feat/auth-login` |
| `fix` | 修复缺陷 | `fix/upload-status` |
| `infra` | 本地环境、容器、CI、部署 | `infra/local-mysql` |
| `docs` | 文档和协作规则 | `docs/ai-rules` |
| `refactor` | 不改变外部行为的代码整理 | `refactor/error-handling` |
| `test` | 补充或修正测试 | `test/workspace-access` |
| `chore` | 依赖、构建或仓库杂项 | `chore/update-wrapper` |

## 3. Commit 格式

提交遵循 Conventional Commits 的结构，说明使用中文：

```text
<类型>(<范围>): <中文摘要>
```

范围可选。它应使用与代码模块一致的小写英文，例如 `auth`、`document`、`chat`、`api`、`db`。

推荐示例：

```text
chore: 初始化 Spring Boot 工程
docs: 建立项目协作规范与 AI 开发规则
infra(db): 添加本地 MySQL 容器环境
feat(auth): 新增密码登录接口
feat(document): 支持上传文件和查询处理状态
fix(chat): 修复历史消息引用丢失
refactor(api): 提取统一异常处理
test(retrieval): 补充工作空间过滤测试
```

提交摘要要求：

- 使用动词开头，例如“新增”“修复”“添加”“调整”“提取”“删除”。
- 说明实际结果，不写“更新”“修改一下”“优化代码”等模糊文字。
- 一行完成，避免句号和无意义英文缩写。
- 一个提交只完成一个可审核意图；不要把无关格式化、依赖升级和业务功能混在一起。

复杂提交可以在正文记录原因和验证结果：

```text
feat(document): 支持上传文件和查询处理状态

为文档创建、对象存储写入和处理状态查询建立最小闭环。

验证：./mvnw test
关联：#12
```

## 4. 提交如何拆分

拆分依据是“能否独立理解和验证”，不是文件数量。

以下内容应放在同一个提交：

- 一个功能所必需的 Controller、Service、DTO、Repository 和测试。
- 某次数据库迁移及依赖该迁移的代码。
- 某个基础设施配置及其本地启动说明。
- 一项接口变更及其 OpenAPI、测试和调用说明。

以下内容应拆成不同提交：

- 业务功能与无关依赖升级。
- 数据库基础设施与后续账号业务。
- 独立可验证的重构与行为变更。
- 临时调试修改与正式实现。

示例：实现“本地 MySQL 与 Flyway 基线”可以是一个提交：

```text
infra(db): 添加本地 MySQL 与 Flyway 基线
```

实现“密码登录”可以是一个提交或多个顺序提交：

```text
feat(auth): 添加用户账号数据模型
feat(auth): 新增密码登录接口
test(auth): 覆盖登录失败和令牌过期场景
```

如果中间提交不能独立构建或测试，不要为了凑“提交数量”强行拆分。

## 5. Issue 规范

重要功能、缺陷和技术债应先建立 GitHub Issue。小型文案修正或明显的一行修复不强制建立。

Issue 标题格式：

```text
[类型] 简短目标
```

示例：

```text
[infra] 建立本地 MySQL、环境变量与 Flyway 基线
[feat] 支持用户密码登录
[fix] 修复文档处理失败后无法重试的问题
```

Issue 正文使用以下模板：

```markdown
## 背景

为什么需要这项工作。

## 目标

- [ ] 可验证目标一
- [ ] 可验证目标二

## 不在本次范围内

- 明确不做的内容

## 验收方式

说明测试、接口、页面或运行结果。
```

为 Issue 添加合适标签，例如 `feature`、`bug`、`infra`、`documentation`、`good first issue`。里程碑日期和计划节奏使用 GitHub Milestone 或 Project 字段表达，不伪造 Issue 创建时间。

## 6. Pull Request 规范

每个 PR 应指向一个明确的 Issue，并在正文中通过 `Closes #编号` 关联。PR 标题与主要提交保持同样的格式，例如：

```text
infra(db): 添加本地 MySQL 与 Flyway 基线
```

PR 正文模板：

```markdown
Closes #编号

## 改动内容

- 本次完成的能力

## 验证结果

- [x] 执行的测试或构建命令
- [x] 手动验证的接口或页面行为

## 配置与部署影响

- 新增的环境变量、迁移脚本或容器服务

## 已知限制

- 本次未覆盖、后续继续处理的内容
```

提交 PR 前检查：

1. 分支只包含本 Issue 相关改动。
2. 测试、构建和必要的手动验证已完成。
3. OpenAPI、README、部署说明或架构文档已按影响范围更新。
4. 暂存区和 diff 中没有密钥、日志、构建产物或本机文件。
5. 数据库迁移、配置变更和回滚影响已写明。

## 7. 合并、发布与时间记录

- 审核通过后合并到 `main`；通常使用 squash merge，让 `main` 保持一个 Issue 一个清晰提交。
- 合并后的功能分支删除，避免长期堆积。
- 每个可运行演示版本打标签，例如 `v0.1.0`。
- 发布说明记录新增能力、升级步骤、数据库迁移和已知限制。
- Git 提交日期应反映真实开发或迁移发生时间；不要为了制造项目履历伪造历史。
- Issue 和 Pull Request 的创建时间保留真实协作过程；网页创建时不能自行选择任意历史时间。

## 8. 权限与质量门禁

- 未经用户在当前任务明确要求，不执行 commit、push、merge、force-push、rebase --onto 或历史改写。
- 文档变更：检查链接、目录、编号和事实一致性。
- 后端变更：运行相关测试；必要时运行 `./mvnw test` 或 `./mvnw package`。
- 接口变更：验证成功、校验失败、未登录、无权限和关键业务失败场景。
- 部署变更：验证配置样例、健康检查、数据持久化和回滚说明。
