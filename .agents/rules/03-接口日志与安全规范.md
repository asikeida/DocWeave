# 接口、日志与安全规范

## 1. HTTP 接口

- 路径使用资源语义和小写连字符，例如 `/api/v1/knowledge-bases`。
- 使用正确的 HTTP 方法和状态码；创建、读取、更新、删除、校验失败和权限失败应有可区分语义。
- 请求与响应使用专门 DTO，不泄漏 Entity 内部字段。
- 接口改动同步维护 OpenAPI 描述，确保 Swagger UI 可用于实际调试。
- 错误响应应包含稳定的业务错误码、对用户可读的消息和可追踪的请求标识；具体格式在首次实现时统一确定。

## 2. 异常处理

- 业务异常在靠近业务规则的位置抛出，由统一异常处理层转换为 HTTP 响应。
- 不吞掉异常，不以空值或“成功但无数据”掩盖失败。
- 客户端不应收到堆栈、SQL、文件路径、密钥或内部实现细节。

## 3. 日志

- 使用 SLF4J 参数化日志，不使用 `System.out.println`。
- 记录关键业务节点：认证失败、权限拒绝、文件上传、异步任务状态、索引操作、模型调用失败和不可恢复异常。
- 每个请求应能关联请求标识；日志应包含定位问题所需的上下文，但不得记录密码、令牌、授权头、完整文件内容或隐私数据。
- 日志级别含义明确：`ERROR` 表示需要处理的失败，`WARN` 表示可恢复风险，`INFO` 记录关键业务事件，`DEBUG` 仅用于诊断。
- 预期的业务校验失败使用带上下文的 `WARN` 日志，通常不记录堆栈；未知系统异常使用 `ERROR` 日志并保留异常对象和堆栈，确保能够定位根因。
- 日志消息使用 SLF4J 的 `{}` 参数化形式，不通过字符串拼接构造；异常上下文必须经过脱敏。

## 4. 健康检查与配置

- 使用 Actuator 的健康检查端点供 Docker、Nginx 或监控系统判断应用是否可用。
- 公网只开放最小必要的健康检查；环境信息、配置详情和指标端点默认不公开。
- 安全配置与业务功能一起测试：未登录、无权限、过期令牌、错误输入和跨工作空间访问都应有明确行为。
