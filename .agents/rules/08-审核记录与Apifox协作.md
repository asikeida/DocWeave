# 审核记录与 Apifox 协作

## 1. 每轮开发的本地审核材料

每轮开发完成后，必须在 `.local/代码审核/` 新建 `YYYY-MM-DD-两位序号-主题.md`，例如 `2026-10-28-01-M1.1账号登录.md`。该目录被 Git 忽略，不提交；不得存放密码、令牌、私钥或真实服务器连接信息。

除前端有关的内容外，本轮所有新增、修改、删除的文件都要覆盖，包括 Java、SQL、配置、依赖、CI、规则及正式文档。前端文件不混入本记录，但仍须按前端规则验证并另行说明。

记录必须包含：

1. 本轮目标、实际范围与未实现能力。
2. 建议阅读顺序和通俗的调用链说明。
3. 逐文件路径、变更类型、原来与现在的区别、原因、关键类或方法、关联文件。
4. 表结构、迁移、配置项及运行影响；不可逆或部署相关的操作单独写清楚。
5. 实际执行的命令、通过/失败/跳过结果及证据位置；历史验证和本轮新验证分开。
6. Git 状态、是否提交/推送、Apifox 同步目标、资源数量、分支与遗留阻塞。
7. 人工审核清单、已知限制和待确认问题。

后续补丁要同步更新记录，避免文档描述与最终 diff 不一致。不能用一句“详见 Git diff”代替解释；也不能把提交 PR 当作已合并。

## 2. Apifox 目标

- 团队：个人团队（ID `4286019`）。
- 项目：DocWeave（ID `8979996`），私有 HTTP 项目。
- 不操作其他团队或公司项目。
- 目标是用户手动创建并已开启 AI 直接编辑权限的项目，分支 main；首次已同步 5 个认证接口、3 个模型与 Bearer 鉴权组件。后续以 CLI 回读为准。
- 另有 CLI 先前创建的同名空项目 ID `8979987`，不是协作目标；不要误写或未经允许删除。

不要将访问令牌写入仓库；使用 CLI 已登录凭据。无需为此预建 `.apifox/settings.json`。CLI 自动生成的 `.apifox/` 状态由 Git 忽略，不作为项目协作配置提交。

## 3. 每次接口开发后的必做步骤

1. 读取可用的 `apifox-cli` 技能，涉及导入时补读 `apifox-import-export`。首次确认 CLI 版本和帮助，不默认升级。
2. 获取目标项目、模块、分支与现有接口，确认没有选错团队。
3. 优先从应用 `/v3/api-docs` 取得 OpenAPI，不手写只有 URL 的路由骨架。检查 tags、请求字段、响应模型和鉴权要求；不得上传实际账号密码或请求中取得的令牌。
4. 统计 paths、operations、schemas、writes、withBody、emptyObjectBodies。Cookie 驱动的 refresh/logout 无 JSON 请求体是设计结果，不能为凑指标虚构请求体。
5. 按当前 CLI help 获取资源格式；支持文件 schema 的 create/update 必须先 `cli-schema get` 与 `cli-schema validate`。只接受 flags 且未提供 schema 的命令按当前 CLI 帮助执行，并在审核材料说明。
6. 对照当前改动同步接口、参数、响应、鉴权、错误码和相关说明。已有接口保持资源身份，禁止每轮 keepBoth 造成重复；覆盖/删除和分支合并按用户授权与技能规则执行。不使用全项目删除未匹配资源来同步局部接口。
7. 写入被权限保护拦截时停止依赖写入，向用户解释并选择方案；不能擅自绕过、开权限、建 AI 分支或合并。
8. 完成后 list/get 回读数量，至少抽查一个读接口和一个写接口，核验请求与响应 schema。实际运行接口测试另行记录；导入文档不等于测试已通过。
9. 在本轮审核 MD 和交付回复中写明项目/分支、同步内容、实际结果和阻塞。

## 4. 同伴测试说明

项目私有，是否邀请同伴及其权限由用户决定。接口文档可通过项目协作使用，但本机地址只供运行服务的电脑访问；同伴需自行运行项目或使用以后部署的测试环境。

当前认证需要先 GET csrf，保留同一 Cookie 会话，再将响应 token 放入 X-XSRF-TOKEN；登录后用返回的 accessToken 测试 me；refresh/logout 需相同 Cookie 会话及 CSRF 请求头。不要把真实登录凭据保存为共享示例或公共变量。
