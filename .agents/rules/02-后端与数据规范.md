# 后端与数据规范

## 1. Spring Boot 与业务层次

- Controller 只处理 HTTP 参数、身份入口、调用服务和返回响应，不承载复杂业务规则。
- Service 负责用例编排、权限判断、事务边界和跨聚合协调。
- Repository 负责持久化查询，不在 Controller 中直接拼接数据库逻辑。
- DTO 用于 API 边界；不要直接把 JPA Entity 作为请求或响应对象暴露。
- 新增请求对象使用 Bean Validation 表达可验证约束，并为校验错误提供一致输出。

## 2. 数据归属与权限

- 所有用户数据都应有明确归属，例如用户、工作空间、知识库或文档。
- 查询、更新和删除必须验证当前用户是否有权访问目标数据。
- 不因为前端隐藏了按钮就省略后端鉴权。
- 多表查询和列表查询必须检查是否遗漏工作空间或用户过滤条件。

## 3. JPA 与事务

- 先写清楚实体关系和数据库约束，再实现 Repository。
- 避免在循环中触发懒加载查询；需要时使用明确的查询、投影或抓取策略。
- 事务放在 Service 的用例边界；不要为了省事给所有查询加写事务。
- 不依赖生产环境中的 `ddl-auto=update` 自动修改表结构。

## 4. Flyway 与数据库迁移

- 从第一张持久化业务表开始使用 Flyway 管理结构变更。
- 每次表结构、索引、约束或必要基础数据变化，都新增一个不可修改的版本化迁移脚本。
- 已在共享环境执行过的迁移脚本不能随意改写；需要修正时创建新的迁移。
- 迁移脚本和依赖它的代码放在同一功能提交中。

## 5. 异步与中间件

- Kafka、MinIO、Redis、Elasticsearch 只在对应业务需求出现后引入。
- 异步任务必须有状态、幂等策略、失败记录和可重试方式。
- 文件原始内容、关系数据、短期缓存和检索索引要有明确职责，不能互相替代。
- 引入一个新基础设施时，补充本地启动方式、配置说明、健康检查和关键失败场景。
