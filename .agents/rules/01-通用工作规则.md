# 通用工作规则

## 1. 先理解再修改

1. 阅读当前任务有关的代码、配置、测试和文档。
2. 明确输入、输出、数据归属和失败场景。
3. 选择最小可行改动，不为假设中的未来需求预建结构。
4. 修改后运行与风险相匹配的验证，并如实记录结果。

不能仅凭“看起来合理”宣称完成。涉及运行时行为时，应优先检查真实请求、响应、日志和持久化数据。

## 2. 代码边界

- 一个类只处理清晰职责；不要把业务规则、HTTP 处理和数据库访问混在同一个类中。
- 业务代码按功能模块聚合。模块之间通过明确的服务、DTO 或接口协作。
- `common` 仅容纳至少两个模块稳定共用的内容；单模块代码放回所属模块。
- 不创建 `Utils` 大杂烩；工具必须有明确、通用且无业务副作用的职责。
- 不进行与当前目标无关的格式化、命名修改或大范围重构。

## 3. 配置与敏感信息

- 配置区分本地、测试、生产环境，并通过环境变量覆盖。
- 示例配置只写变量名、用途和安全占位值。
- 密钥、密码、私钥、生产地址、真实用户数据和完整日志样本不得进入 Git。
- 发现已跟踪的敏感信息时，不在回复中复制其值；报告文件位置并停止传播。

## 4. 文档与注释

- 公共行为、重要限制、复杂业务决策应写入正式文档。
- 注释解释“为什么”，不重复代码已经表达的“做什么”。
- 未整理的分析过程写进 `.local/`，不污染正式文档。
- 文档中的未来设想必须标为“规划”，不能伪装成当前实现。

## 5. 完成标准

一项开发任务至少应能回答：

1. 改动解决了什么问题？
2. 改动影响了哪些模块和接口？
3. 通过什么方式验证？
4. 有哪些已知限制或下一步？
